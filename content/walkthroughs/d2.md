# Tool Design & MCP Integration

Domain 2 carries 18% of the exam. It covers how to describe and shape tools so Claude picks the right one, how tools should report errors, how to spread tools across agents and control when they're called, how to wire MCP servers into Claude Code, and how to use the built-in file and search tools well.

Facts about API, MCP, and Claude Code behavior on this page were checked on 2026-11-07 against the [define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [Claude Code MCP](https://code.claude.com/docs/en/mcp), [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference), and [subagents](https://code.claude.com/docs/en/agent-sdk/subagents) docs.

## Tool interfaces and descriptions
<!-- concepts: tool-descriptions, tool-selection, tool-naming, tool-overlap, system-prompt-tool-conflicts, tool-consolidation, tool-splitting, input-schema-design, tool-response-design, high-signal-output, input-examples, parameter-descriptions -->

### Core concepts

- The description is the main thing Claude uses to choose a tool. Current docs call detailed descriptions "by far the most important factor in tool performance".
- A good description covers what the tool does, when to use it (and when not to), what each parameter means, what comes back, and what it doesn't cover. Aim for at least three or four sentences.
- Tools with overlapping names and descriptions get confused with each other. Prefixing names by service (`crm_get_contact`, `app_get_account`) makes the boundary obvious.
- A system prompt rule triggered by a keyword ("whenever the user mentions an order...") can override good descriptions.
- `input_examples` show valid inputs for complex or format-sensitive parameters. Each example must match the schema.
- Tool results should return only high-signal fields, with stable, meaningful identifiers rather than internal keys.

### Decision rules

- Many near-identical operations on one resource: consolidate them into one tool with an `action` parameter. This is the current docs' recommendation.
- One tool hiding several different input and output contracts behind a mode flag: split it, so each tool's schema allows only valid inputs.
- Claude picks the wrong tool: first make the descriptions and names distinct. Only then consider routing or examples.
- Malformed arguments for a strict format: describe the format in the parameter description and add `input_examples`.

### Common mistakes

- One-line descriptions such as "Gets an invoice."
- Descriptions full of implementation details (endpoints, retries) instead of usage guidance.
- Over-broad trigger words that pull unrelated requests into one tool.
- Returning whole database rows, so Claude quotes internal IDs.

## Structured error responses
<!-- concepts: mcp-iserror, tool-execution-errors, structured-errors, retryable-errors, error-categories, business-rule-errors, access-failure-vs-empty, local-error-recovery, error-propagation -->

### Core concepts

- MCP separates two kinds of error. Protocol errors (JSON-RPC errors) are for problems with the request, such as an unknown tool. Tool execution errors, such as API failures, invalid data, or business-logic errors, come back in the tool result with `isError: true`, so the model can see them and react.
- The same message for every error ("Operation failed") hides what the agent needs to know: can trying again help?
- Useful error metadata: a category (transient, validation, permission, business), an `isRetryable` flag, and a readable message, which for business-rule errors should be suitable for the end user.
- An access failure (the service was unreachable) and a valid empty result (nothing matched) are different outcomes and must look different.

### Decision rules

- Upstream failure: return `isError: true` with a description, not an empty success and not silence.
- Policy outcome (outside a cancellation window, over a limit): non-retryable business error with an explanation the agent can pass on.
- Transient failures in a subagent: retry locally a bounded number of times, then pass up only what's unresolved, with what was tried and any partial results.

### Common mistakes

- Returning an empty list during an outage, so the agent tells users they have no records.
- Retrying every error the same way, so the agent hammers invalid input and gives up on timeouts.
- Sending every routine timeout to the coordinator, which then re-plans and fills its context.

## Distributing tools and controlling tool choice
<!-- concepts: scoped-tool-access, tool-count, constrained-tools, tool-choice, forced-tool-use, model-differences, strict-tool-use -->

### Core concepts

- The more tools one agent has, the harder each choice becomes. Specialist subagents with small, role-specific tool sets choose more reliably.
- A constrained tool (`load_doc(doc_id)`) can only reach what it should, where a generic one (`fetch_url`) can reach anything.
- `tool_choice` options:
  - `auto`, the default: Claude may call a tool or answer directly.
  - `any`: Claude must call one of the tools and picks which.
  - `tool`: Claude must call the named tool.
  - `none`: no tool calls.
- A forced call (`any` or `tool`) skips thinking: the response starts with the `tool_use` block.
- **Model differences:** Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1, and Claude Mythos 5.1 reject `any` and `tool` with a 400 error. Models such as Claude Opus 5 and Claude Haiku 5.5 accept them. The exam guide predates this change.

### Decision rules

- Unknown document type, and a tool call must happen, on a model that supports forced tool use: `any`.
- One step must run first: force that tool on the first request, then switch to `auto`.
- Claude should reason before calling a tool: use `auto` and name the tool in the prompt.
- On models that reject forced tool use: use `auto` with an explicit instruction and `strict: true`, and check that a call was made (retry if not). Use structured outputs when the call only existed to get JSON back.

### Common mistakes

- Answering selection errors on a 22-tool agent with a longer prompt instead of fewer tools per agent.
- Forcing one specific tool when the right tool depends on the input.
- Treating the 400 from a forced `tool_choice` as a temporary error and retrying it.

## MCP servers in Claude Code
<!-- concepts: mcp-scopes, project-scope, local-scope, mcp-env-expansion, credential-management, mcp-resources, context-efficiency, mcp-tool-descriptions, build-vs-reuse, mcp-integration -->

### Core concepts

- Scopes:
  - **Local** (the default): private to you, this project only, stored in `~/.claude.json` under the project's path.
  - **Project**: shared through version control in `.mcp.json` at the project root.
  - **User**: private to you, in all your projects, stored in `~/.claude.json`.
- `.mcp.json` supports environment variables: `${VAR}` and `${VAR:-default}` in `command`, `args`, `env`, `url`, and `headers`. A variable that isn't set and has no default is left as literal text.
- MCP resources expose content such as schemas or documentation. In Claude Code you reference them with `@server:protocol://resource/path`, and they're fetched as attachments.
- Tool search is on by default: MCP tool definitions are deferred and loaded when needed, so many servers don't fill the context up front.
- Claude chooses MCP tools from their descriptions, just like built-in tools.

### Decision rules

- Team-wide server: project scope (`.mcp.json`) with secrets as `${VAR}` references.
- Personal and experimental, one project only: local scope. Personal and in every project: user scope.
- Agent keeps exploring to find out what data exists: expose a catalog as resources.
- Standard integration (such as Jira): use an existing server. Team-specific system: build a custom one.

### Common mistakes

- Committing tokens in `.mcp.json`, or "hiding" them with base64.
- Describing MCP servers in `CLAUDE.md` and expecting that to configure them.
- Thin MCP tool descriptions, so Claude keeps using built-in search instead.

## Built-in tools
<!-- concepts: built-in-tools, content-search, file-name-search, edit-tool, unique-matching, incremental-exploration, wrapper-tracing -->

### Core concepts

- Content search finds lines inside files (Grep). Name-pattern search finds files by path (Glob, with patterns such as `**/*.spec.ts`).
- On macOS, Linux, and WSL, current Claude Code leaves Glob and Grep out of the default tool set, and Claude runs `find` and `grep` through Bash instead. Glob and Grep come back when you name them in `--tools` or `--allowedTools` (or the Agent SDK equivalents), or when a subagent lists them without Bash. The exam guide describes Glob and Grep as always present.
- `Edit` does exact string replacement. `old_string` must appear exactly once; otherwise Claude adds surrounding context to make it unique, or sets `replace_all: true` to change every occurrence.
- `Read` loads whole files, and `Write` creates or overwrites them.

### Decision rules

- "Who calls this function?": content search. "Which files are tests?": name-pattern search.
- Edit fails on a non-unique match: extend `old_string` with nearby lines. Use `replace_all` only when every occurrence should change. A full `Write` should start from a fresh `Read`, never from memory.
- Unfamiliar codebase: search for entry points, then read outward along imports and calls.
- Wrappers that re-export under aliases: list every exported name first, then search for each.

### Common mistakes

- Using a file-name pattern to find callers.
- Reading every file up front and running out of context.
- Searching only for a function's original name when wrappers re-export it under other names.

## Checklist: what to do without notes

- [ ] Write a four-sentence description for a tool that says what it returns, when to use it, and what it doesn't cover.
- [ ] Decide between consolidating tools under an `action` parameter and splitting a mode-switching tool.
- [ ] Explain the difference between an MCP protocol error and `isError: true`, and give an example of each.
- [ ] Sketch an error payload with a category, a retry flag, and a message.
- [ ] Explain why an outage must not look like an empty result.
- [ ] Pick `auto`, `any`, a named `tool`, or `none` for a described pipeline, and say what changes on models that reject forced tool use.
- [ ] Place an MCP server in local, project, or user scope, and keep its secrets out of git.
- [ ] Choose between content search and name-pattern search, and recover from a non-unique `Edit`.
