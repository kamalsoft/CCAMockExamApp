# Context Management & Reliability

Domain 5 carries 15% of the exam. It covers keeping critical facts intact across long interactions, knowing when to escalate, propagating errors so a coordinator can recover, working in large codebases without losing the thread, routing limited human review, and keeping track of where every claim came from.

Facts on this page were checked on 2026-11-07 against the [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [subagents](https://code.claude.com/docs/en/agent-sdk/subagents), and [memory](https://code.claude.com/docs/en/memory) docs. Much of this domain is design judgment rather than API behavior.

## Preserving critical information
<!-- concepts: case-facts, progressive-summarization, tool-output-trimming, context-budget, long-context-ordering, document-tagging, lost-in-the-middle, input-structure, conversation-history, stateless-api, structured-handoffs, issue-tracking -->

### Core concepts

- Summaries blur exact values: "$1,284.50 by June 3" becomes "a refund soon". Keep transactional facts (amounts, dates, IDs, commitments) in a persistent **case-facts block** outside the summarized history, and send it in every prompt. Track multiple issues as separate structured records.
- Tool results pile up in context. Trim them to the fields the task needs before they're appended.
- The Messages API is **stateless**: each request must carry the conversation history it needs. Prompt caching makes the repeated prefix cheap.
- For long inputs, put the documents first, each in `<document>` tags with its source, and the question last. In Anthropic's tests this improved response quality by up to 30%.
- Models handle the start and end of long inputs best and can miss the middle. Lead with a key-findings summary and use clear section headers.
- When a downstream agent has a tight budget, change the upstream agents to return structured facts, citations, and relevance instead of verbose reasoning.

### Common mistakes

- Trusting a summary to keep exact figures.
- Sending only the latest message and expecting the API to remember.
- Truncating verbose reports, which keeps the reasoning and drops the conclusions.

## Escalation and ambiguity
<!-- concepts: escalation, explicit-escalation-request, frustration-handling, policy-gaps, ambiguous-matches, clarification, progress-based-escalation -->

### Core concepts

- Good escalation triggers:
  - the customer explicitly asks for a person (honor it immediately);
  - policy is silent or ambiguous about the request;
  - the agent can't make meaningful progress.
- Frustration on its own isn't a trigger. When the issue is within the agent's ability, acknowledge the feeling and resolve it, and escalate if the customer then asks for a person.
- Sentiment and self-reported confidence are poor proxies for how complex a case is. Explicit criteria, illustrated with examples, work better.
- Several matching records call for a clarifying question (email, order number), never a guess.

### Common mistakes

- Investigating first when the customer asked for a human.
- Inventing policy by analogy, in either direction.
- Escalating criteria that cover requests and limits but not "stuck".

## Error propagation in multi-agent systems
<!-- concepts: error-propagation, partial-results, coverage-annotations, failure-isolation, error-context-use, retry-placement -->

### Core concepts

- Useful error context includes the failure type, what was attempted, any partial results, and possible alternatives, so the coordinator can recover sensibly.
- Two anti-patterns: silently returning empty results as success, and ending the whole workflow because of one failure.
- Retries at several layers multiply (3 × 3 × 3 = 27 attempts). Retry transient errors once, in a bounded way, close to the failure, and let the layers above propagate instead of retrying.
- Final outputs should carry coverage notes: which findings are well supported, and which areas have gaps because a source failed.

### Decision rules

- One of many parallel tasks fails: keep the completed results and report the failure with its context.
- Partial results and a deadline: use what you have, retry the rest if there's time, and disclose the gaps.

## Context in large codebase exploration
<!-- concepts: context-degradation, scratchpad-files, phase-summaries, subagent-context-passing, crash-recovery, state-persistence, manual-compaction, compaction-limits, persistent-instructions -->

### Core concepts

- In long sessions context degrades, and answers drift from "the `RefundService` in `billing/`" to "services like this typically...". A scratchpad file of key findings keeps the specifics available to consult.
- Subagents explore in their own context and return summaries. Between phases, summarize what was established and put that summary into the next phase's subagent prompts.
- For crash recovery, each agent exports its state to a known location, and on resume the coordinator loads a manifest and injects that state into prompts.
- `/compact` summarizes older history to free space. Compaction can drop specific early instructions, so rules that must persist belong in `CLAUDE.md`, which is re-injected on every request. If a rule must never break, enforce it with a hook.

### Common mistakes

- `/clear` mid-task, which loses everything.
- Passing whole transcripts between phases.
- Turning off compaction instead of moving persistent rules to `CLAUDE.md`.

## Human review and confidence calibration
<!-- concepts: human-review, segmented-accuracy, stratified-sampling, review-routing, conflicting-sources, confidence-calibration, field-level-confidence -->

### Core concepts

- Overall accuracy can hide weak segments: 97% overall can include 70% on handwritten receipts. Validate accuracy by document type and field before reducing review.
- After automating high-confidence items, keep a **stratified random sample** under review to measure the ongoing error rate and catch new error patterns.
- Field-level confidence is useful for routing only after it's calibrated: measure accuracy against a labeled validation set and set a threshold for each field.
- Limited reviewer time should go to low-confidence items, and to documents with ambiguous or contradictory sources.

### Common mistakes

- One "feels high" threshold for every field.
- Averaging field confidences, which hides the weak fields.
- Reviewing only what customers complain about.

## Provenance and uncertainty in synthesis
<!-- concepts: provenance, claim-source-mapping, conflicting-sources, temporal-data, evidence-strength, content-type-rendering, synthesis-output -->

### Core concepts

- Attribution is lost when findings are compressed without their sources. Subagents should send structured **claim-source mappings** (URL, document, excerpt) that synthesis preserves and merges.
- When credible sources conflict, report both values with their sources and flag the conflict. Don't average them, and don't silently pick one.
- Dates on every finding stop changes over time from looking like contradictions.
- Reports should separate well-established findings from contested ones, keeping each source's own characterization.
- Format follows content: financial data in tables, news in prose, technical findings in structured lists.

## Checklist: what to do without notes

- [ ] Design a case-facts block and per-issue records for a long support conversation.
- [ ] Lay out a long-context prompt: tagged documents first, question last.
- [ ] List three escalation triggers, and say why sentiment isn't one of them.
- [ ] Design error context and coverage notes, and decide where retries belong.
- [ ] Plan a multi-phase exploration with scratchpads, phase summaries, and crash recovery.
- [ ] Say what compaction may lose, and where persistent rules belong.
- [ ] Calibrate field-level thresholds and set up stratified sampling.
- [ ] Merge findings from several sources while keeping attribution, conflicts, and dates.
