# Prompt Engineering & Structured Output

Domain 4 carries 20% of the exam. It covers writing criteria Claude can apply precisely, steering output with examples, getting reliably structured data out, validating and retrying extractions, running large jobs through the Message Batches API, and designing reviews that catch what a single pass misses.

Facts on this page were checked on 2026-11-07 against the [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), and [batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) docs.

## Explicit criteria
<!-- concepts: explicit-criteria, precision, false-positive-management, developer-trust, severity-criteria, instruction-context, confidence-filtering -->

### Core concepts

- Claude follows clear, specific instructions best. Vague words ("important", "be conservative", "high-confidence only") leave the boundary to interpretation and barely move precision.
- Categorical criteria say what to report and what to skip: bugs and security in, style and local idioms out.
- Explaining *why* a rule exists ("replies go out as SMS, which shows markup as raw text") lets Claude generalize to cases the rule didn't list.
- One noisy category erodes trust in the accurate ones.

### Decision rules

- Precision problem: replace general caution with explicit report/skip criteria.
- Inconsistent ratings: define each level with concrete examples.
- A category with a high false-positive rate: pause it, fix its criteria, and keep the accurate categories running.
- Self-reported confidence is weak until it's calibrated against labeled data. Don't use it as a substitute for clear criteria.

### Common mistakes

- Stacking more caution wording on a prompt that already failed with it.
- Repeating a rule in capital letters instead of giving its reason.
- Turning everything off because one category is noisy.

## Few-shot examples
<!-- concepts: few-shot-examples, output-consistency, few-shot-diversity, few-shot-ambiguity, reasoning-examples, few-shot-extraction, hallucination-reduction, few-shot-structure-variety -->

### Core concepts

- Examples are one of the most reliable ways to steer format, tone, and structure when instructions alone give inconsistent results.
- Good examples are relevant to the real use case, diverse enough to avoid unintended patterns, and wrapped in `<example>` tags (with `<examples>` around several). Current docs suggest 3–5. The exam guide says 2–4. Either way, a few well-chosen examples beat many similar ones.
- Examples for ambiguous cases should show *why* one choice beat a plausible alternative, so Claude learns the judgment, not just the answer.
- In extraction, examples that show informal values ("a pinch") kept as text, with numeric fields left null, reduce made-up precision. Examples that cover varied document structures (inline citations vs bibliographies) fix structure-dependent misses.

### Common mistakes

- Examples all from one area, so their topic leaks into unrelated output.
- Adding more prose rules where an example would settle the question.
- Making a numeric field required, which forces Claude to invent a number.

## Structured output
<!-- concepts: structured-outputs, json-schema, semantic-validation, nullable-fields, schema-design, enum-other-pattern, strict-tool-use, stop-reason-handling -->

### Core concepts

- Structured outputs constrain decoding to a schema, which eliminates JSON syntax errors. There are two forms:
  - **JSON outputs** (`output_config.format`) shape Claude's whole response.
  - **Strict tool use** (`strict: true` on a tool) guarantees that the tool's inputs match its schema.
- They guarantee **shape, not meaning**. Line items can still fail to add up, and values can land in the wrong field.
- Schema limits: no recursive schemas, no `minimum` or `maximum`, no string-length constraints, and `additionalProperties` must be `false`. Unsupported keywords return a 400 error. The capitalization of enum values isn't guaranteed, so compare them case-insensitively.
- A refusal or `max_tokens` cut-off can produce output that doesn't match the schema. Check `stop_reason` before parsing.

### Decision rules

- Response *is* the data (extraction): JSON outputs. Claude chats *and* calls a tool that needs valid arguments: strict tool use on that tool.
- Information that may be absent: make the field nullable and say "use null when absent".
- Open-ended categories: an enum plus `"other"` with a detail field, and `"unclear"` for ambiguous inputs.
- Arithmetic and cross-field rules: check them in code.

## Validation, retry, and feedback loops
<!-- concepts: retry-with-feedback, validation-loop, retry-limits, missing-information, feedback-loops, detected-pattern, self-correction, conflict-detection -->

### Core concepts

- Retry with feedback: send the original document, the failed extraction, and the *specific* validation errors. An identical retry tends to repeat the identical mistake.
- Retries fix format and structural errors. They can't produce information that isn't in the input: an amendment that was never sent, or a tax ID the document doesn't contain.
- Extracting both `stated_total` and `calculated_total`, with a `conflict_detected` flag, exposes source errors without silently "fixing" them.
- A `detected_pattern` field on each finding turns developer dismissals into data you can analyze by pattern.

### Decision rules

- Fixable format error: retry with feedback.
- Value absent from the source: record it as missing and flag it, with no retry.
- Inconsistent source data: capture both values and flag the conflict for review.

## Batch processing
<!-- concepts: message-batches, cost-optimization, batch-custom-id, batch-sla-planning, batch-failure-handling, batch-limitations, client-tools, prompt-refinement -->

### Core concepts

- The Message Batches API costs 50% less. Most batches finish within an hour, but results are only guaranteed within 24 hours, and a batch that doesn't finish in 24 hours expires. There's no latency guarantee.
- Limits: 100,000 requests or 256 MB per batch. Results stay available for 29 days.
- Results can come back in **any order**. Match them to requests by `custom_id`.
- Each request runs independently. Requests can carry tool definitions and multi-turn history, but nothing runs your own (client) tools during the batch, so a request that stops on `tool_use` needs another round. `stream`, fast mode, and `fallbacks` aren't supported in batches.

### Decision rules

- Nobody waiting on results (nightly, weekly): batch. Someone blocked on the answer: synchronous API.
- Meeting an SLA: submission interval plus 24 hours must fit inside it.
- Failures: resubmit only the failed `custom_id`s, with whatever fix caused them (such as chunking oversized documents).
- Before a huge batch, refine the prompt on a representative sample.
- Requests that would need your tools: fetch the data up front and put it in the prompt.

## Multi-pass and multi-instance review
<!-- concepts: multi-pass-review, integration-pass, confidence-routing, review-prioritization, independent-review, self-review-limits -->

### Core concepts

- One pass over many documents or files spreads attention thin. Focused per-item passes, plus a separate cross-item consistency pass, catch both local issues and conflicts between items.
- A session that generated work keeps its own reasoning and is less likely to question it. An independent instance, given only the spec and the output, reviews what was actually produced.
- Model-reported confidence becomes useful for routing once thresholds are calibrated against labeled examples. Send low-confidence items to people.

### Common mistakes

- Raising effort or asking the same session to look again, instead of using a fresh reviewer.
- Reviewing summaries, which drop the exact terms where conflicts hide.
- Routing reviewer time by age or at random.

## Checklist: what to do without notes

- [ ] Rewrite a vague instruction as explicit report/skip criteria, and add the reason behind a rule.
- [ ] Choose a few examples that are relevant, diverse, and tagged, including one ambiguous case with its reasoning.
- [ ] Choose between JSON outputs and strict tool use, and design nullable, `"other"`, and `"unclear"` fields.
- [ ] Say which errors structured outputs prevent, and which still need code checks.
- [ ] Build a retry message with feedback, and say when not to retry.
- [ ] Plan a batch around an SLA, match results by `custom_id`, and resubmit only the failures.
- [ ] Design a review with per-item passes, an integration pass, and an independent reviewer.
