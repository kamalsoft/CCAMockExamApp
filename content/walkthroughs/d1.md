# Agentic Architecture & Orchestration

Domain 1 carries 27% of the exam, the largest share. It covers how an agent loop runs, how a coordinator splits work across subagents, how to enforce rules that must never be broken, and how to manage sessions. The questions test judgment: which design fits a constraint, and why the plausible alternatives fail.

Facts about SDK and API behavior on this page were checked on 2026-11-07 against the [agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [subagents](https://code.claude.com/docs/en/agent-sdk/subagents), [hooks](https://code.claude.com/docs/en/agent-sdk/hooks), [sessions](https://code.claude.com/docs/en/agent-sdk/sessions), and [stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) docs.

## Agentic loops
<!-- concepts: agentic-loop, agentic-loop-termination, stop_reason, tool-result-handling, parallel-tool-calls, max-turns, cost-control, model-driven-tool-selection, max-tokens-handling -->

### Core concepts

- A loop sends the conversation to Claude, reads `stop_reason`, runs any requested tools, appends the results, and sends again.
- `stop_reason` is the control signal. `"tool_use"` means Claude is waiting for tool results. `"end_turn"` means the response is complete. `"max_tokens"` means the output was cut off. `"refusal"` means Claude declined.
- A response can contain text and `tool_use` blocks together. Text alone never means "done".
- The assistant turn is appended whole (`response.content`). The next user message holds one `tool_result` block per `tool_use` block, matched by `tool_use_id`, and nothing else.
- Claude chooses each next tool from the request and the results so far. That is what makes it an agent rather than a fixed script.
- In the Agent SDK, a run that finishes normally ends with a `success` result. Hitting `max_turns` or `max_budget_usd` ends it with `error_max_turns` or `error_max_budget_usd`, and those results carry no `result` text.

### Decision rules

- Branch on `stop_reason`. Never parse the model's prose to decide whether the loop is finished.
- Return every tool result for a turn in a single user message, including failures (`is_error: true`).
- Treat `max_tokens` as "incomplete". If a `tool_use` block was cut off, retry with a higher `max_tokens`; never run a truncated tool call.
- Use turn and budget limits as backstops. A limit set below what the task needs turns every run into a failure.

### Common mistakes

- Stopping when the response contains text, which skips the tool call that came with it.
- Splitting parallel results across messages, or adding text after the results.
- Treating any non-`tool_use` stop reason as success, which hides truncation and refusals.
- Hard-coding the tool order, so every request pays for tools it doesn't need.

## Coordinators and subagents
<!-- concepts: hub-and-spoke, coordinator-routing, observability, dynamic-subagent-selection, coordinator-role, iterative-refinement, coverage-evaluation, scope-partitioning, parallel-subagents -->

### Core concepts

- In a hub-and-spoke design, a coordinator decomposes the task, delegates to subagents, and aggregates their results. Subagents report to the coordinator, not to each other.
- Routing everything through the coordinator gives one place for logging, error handling, and control over what each subagent sees.
- The coordinator decides which subagents a request needs. A simple lookup should not run the whole pipeline.
- Subagents can run in parallel. Independent work then finishes in the time of the slowest subagent rather than the sum of all of them.

### Decision rules

- Match the subagents to the query. Invoke only the ones the request needs.
- Partition scope before work starts, by subtopic or by source type, so parallel subagents don't cover the same ground.
- When coverage matters, let the coordinator check the synthesis against explicit criteria and send targeted follow-up work for the gaps, then synthesize again.
- When a report misses whole areas, check the coordinator's decomposition first. Subagents can only cover what they were assigned.

### Common mistakes

- Letting subagents call each other directly, which makes failures hard to trace and error handling inconsistent.
- Running every subagent on every request "to be safe".
- Re-running the same queries and hoping coverage improves.

## Spawning subagents and passing context
<!-- concepts: subagent-context-isolation, context-passing, structured-context-passing, attribution, agent-definition, tool-restriction, coordinator-prompt-design, subagent-adaptability, subagent-description, delegation -->

### Core concepts

- A subagent that is not a fork starts with a fresh context. It does not see the parent's conversation history, tool results, or system prompt. The prompt the parent writes for it is the only context it receives from the parent.
- Only the subagent's final message returns to the parent, which keeps the parent's context small.
- An `AgentDefinition` sets a subagent's `description`, its system `prompt`, its `tools`, and optionally its `model`. If `tools` is omitted, the subagent inherits every tool available to subagents.
- Claude decides when to delegate by matching the task against each subagent's `description`.
- Claude spawns subagents with a dedicated tool. Current docs name it `Agent`; it was called `Task` before Claude Code v2.1.63, and the exam guide uses the older name.
- `allowedTools` auto-approves the tools it lists. It does not remove the others; those still go through the normal permission flow.

### Decision rules

- Put everything a subagent needs (findings, file paths, decisions) directly in its prompt.
- Pass findings as structured records that keep the claim separate from its source, document, and page, so attribution survives each handoff.
- Restrict a subagent's capabilities with its `tools` list. A prompt instruction like "do not edit files" is guidance, not a guarantee.
- Write descriptions that say what the subagent does and when to use it.
- Give subagents goals and quality criteria rather than rigid step-by-step procedures, so they can adapt to inputs the procedure didn't anticipate.
- To run independent subagents in parallel, request them all in one response.

### Common mistakes

- "Synthesize the findings from earlier", which assumes the subagent can see history it never received.
- Passing findings as prose and expecting the model to keep citations straight.
- Trying to restrict a subagent through the parent's `allowedTools`.
- Vague descriptions such as "Helper agent", which mean the subagent never gets chosen.

## Enforcement and handoffs
<!-- concepts: programmatic-enforcement, prerequisite-gates, structured-handoff, escalation, request-decomposition, multi-concern-handling, programmatic-vs-prompt-enforcement, proportionate-design -->

### Core concepts

- Prompt instructions make behavior likely, not certain. Some failure rate always remains.
- Programmatic enforcement (a prerequisite gate in code, or a hook) makes a rule deterministic: the blocked action cannot run until the condition holds.
- A handoff to a human who can't see the conversation must carry everything they need: identifiers, what was observed, what was tried, the likely cause, and a recommended next step.
- A message with several independent requests should be split into items, each item handled, and one combined reply sent.

### Decision rules

- If breaking a rule causes financial, legal, or safety harm, enforce it in code. If an occasional miss is acceptable (tone, style), keep it in the prompt.
- Block the downstream action until its prerequisite has succeeded for the same entity, such as the same employee or record.
- Prefer prevention to detection. An audit after the fact doesn't undo the action.
- Keep enforcement proportionate. Don't build blocking machinery for preferences.

### Common mistakes

- Answering a 3% violation rate with stronger wording, capital letters, or more examples.
- Escalating with a one-line note, or with a raw transcript nobody will read.
- Answering only the first of several requests in a message.

## Hooks
<!-- concepts: post-tool-use-hook, data-normalization, pre-tool-use-hook, policy-enforcement, deny-behavior, hook-matchers, defense-coverage -->

### Core concepts

- `PreToolUse` hooks run before a tool executes. They can allow, deny, or ask, and they can rewrite the tool's input.
- When a `PreToolUse` hook denies a call, the tool doesn't run. Claude receives the denial and its reason as the tool result and usually tries another approach. The session continues.
- `PostToolUse` hooks run after a tool returns and before Claude sees the result. They can add context or replace the output (`updatedToolOutput`), which makes them the place to normalize data.
- A hook's `matcher` matches tool names, not file paths or other arguments. To filter by path, check `tool_input` inside the hook.
- Hooks run in your application's process, not in the model's context.

### Decision rules

- Use `PreToolUse` to prevent policy violations, and have the denial reason point to the right alternative, such as an escalation or change process.
- Use `PostToolUse` to normalize inconsistent tool outputs (dates, units, status codes) before the model reasons over them.
- Cover every tool that can perform the risky action. A `Write|Edit` hook doesn't see writes made through `Bash`.

### Common mistakes

- Using `PostToolUse` to "block" an action that has already happened.
- Expecting a `PreToolUse` hook to change a tool's output; there is no output yet when it runs.
- Writing a matcher such as `"secrets/*"`, which never matches any tool name.

## Task decomposition
<!-- concepts: prompt-chaining, task-decomposition, adaptive-decomposition, prioritization, dynamic-decomposition, prompt-chaining-tradeoffs -->

### Core concepts

- Prompt chaining runs a fixed sequence of focused steps. It gives predictable, repeatable output when the steps are known in advance.
- Dynamic (adaptive) decomposition plans the next step from what the last one found. It suits open-ended work.
- For unfamiliar or large work, map the structure first, find the highest-impact areas, then plan, and adjust the plan as dependencies come to light.

### Decision rules

- Stable, repeatable checklist: use a prompt chain.
- Next step depends on findings (debugging, investigation, exploration): use dynamic decomposition.
- Prioritize by impact, not by file order or file size.

### Common mistakes

- Forcing novel investigations through a fixed runbook that ends in the same action every time.
- Putting dozens of documents and checks into one pass.
- Giving an open-ended goal to a process that should follow a defined checklist.

## Sessions
<!-- concepts: session-resumption, stale-context, session-forking, targeted-reanalysis -->

### Core concepts

- A session is the saved conversation: prompts, tool calls, tool results, and responses. Resuming restores all of it.
- Sessions save the conversation, not the filesystem.
- Forking (`fork_session` in Python, `forkSession` in TypeScript) creates a new session that starts with a copy of the history. The original stays unchanged, so two approaches can branch from one analysis.
- Forking branches only the conversation. File edits made in one branch are visible to the other.

### Decision rules

- Most prior context still valid: resume, and name the specific files that changed so the agent re-reads them.
- Most prior context stale (for example, after a large refactor): start a new session seeded with a short, structured summary of conclusions that still hold.
- Two alternatives from the same starting analysis: fork.

### Common mistakes

- Resuming after a large refactor without saying anything, so the agent reasons from outdated files.
- Using `/compact` to "forget" stale content; compaction summarizes it rather than removing it.
- Resuming the same session twice to explore two alternatives, which mixes both into one history.
