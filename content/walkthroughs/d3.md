# Claude Code Configuration & Workflows

Domain 3 carries 20% of the exam. It covers where instructions live and how they load, how to package repeatable work as skills, how to scope conventions to file paths, when to plan before editing, how to steer Claude toward the result you want, and how to run Claude Code in CI.

Claude Code changes quickly. Facts on this page were checked on 2026-11-07 against the [memory](https://code.claude.com/docs/en/memory), [skills](https://code.claude.com/docs/en/skills), [non-interactive mode](https://code.claude.com/docs/en/headless), and [common workflows](https://code.claude.com/docs/en/common-workflows) docs.

## CLAUDE.md hierarchy and imports
<!-- concepts: claude-md-hierarchy, user-vs-project-scope, claude-md-local, claude-md-imports, modular-instructions, claude-md-loading, instruction-conflicts, claude-rules-directory -->

### Core concepts

- Where instructions live, from broadest to most specific:

  | Location | Applies to | Shared? |
  | --- | --- | --- |
  | Managed policy | Every user in the organization | Yes, set by IT |
  | `~/.claude/CLAUDE.md` | You, in all your projects | No |
  | `./CLAUDE.md` or `./.claude/CLAUDE.md` | The project, for the whole team | Yes, through version control |
  | `./CLAUDE.local.md` | You, in this project only | No; add it to `.gitignore` |

- Files are **concatenated, not overridden**. Content runs from the filesystem root down to the working directory, so instructions closer to where you launched Claude are read last.
- `CLAUDE.md` files in directories above the working directory load at launch. Files in subdirectories load once Claude reads, writes, or edits a file in that subdirectory.
- `@path/to/file` imports another file. Relative paths resolve from the file containing the import, and imports can nest up to four levels.
- `.claude/rules/` holds topic files (`testing.md`, `api.md`). Rules without `paths` frontmatter load at launch, with the same priority as the project `CLAUDE.md`.

### Decision rules

- Team conventions: project `CLAUDE.md`. Personal preferences everywhere: `~/.claude/CLAUDE.md`. Personal notes for one project: `CLAUDE.local.md`.
- Shared standards needed by some packages: `@import` them from each package's `CLAUDE.md`.
- One large file edited by many teams: split it into `.claude/rules/` topic files.
- Conflicting instructions at different levels: state the scope and the override explicitly, because nothing overrides automatically.

### Common mistakes

- Putting team rules in your own `~/.claude/CLAUDE.md`, so new teammates never get them.
- Assuming a subdirectory `CLAUDE.md` replaces the root one.
- Copying shared standards into every package instead of importing them.

## Skills and custom commands
<!-- concepts: skills, skill-invocation-control, skill-context-fork, context-isolation, subagent-context-isolation, skills-vs-claude-md, skill-frontmatter, argument-hint, skill-allowed-tools, tool-restriction, skill-precedence, personal-skills -->

### Core concepts

- A skill is `.claude/skills/<name>/SKILL.md` (project, shared through git) or `~/.claude/skills/<name>/SKILL.md` (personal). Custom commands have been merged into skills: `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`.
- By default only the skill's `description` sits in context, and its body loads when the skill is used. Claude can also load it automatically when it judges it relevant. `CLAUDE.md`, by contrast, loads in every session.
- Frontmatter fields:
  - `description`: what the skill does and when to use it.
  - `disable-model-invocation: true`: only you can invoke it.
  - `user-invocable: false`: only Claude can invoke it.
  - `argument-hint`: shown in autocomplete, for example `[issue-number]`.
  - `context: fork` (optionally with `agent`): runs the skill as a subagent.
  - `allowed-tools`: tools Claude may use without asking during that turn.
- A forked skill's subagent doesn't see the conversation history. The skill's content is its whole prompt, and only its result comes back.
- **`allowed-tools` grants, it doesn't restrict.** Current docs describe it as tools Claude can use without asking. To limit tools, fork the skill into a subagent whose tool list is restricted, or add deny rules. The exam guide describes it as a restriction.
- When a personal and a project skill share a name, the personal one runs for that user.

### Decision rules

- Always-applicable rules: `CLAUDE.md`. Occasional multi-step procedures: a skill.
- Dangerous or deliberate workflows (deploys): `disable-model-invocation: true`.
- Verbose or exploratory skills: `context: fork`. Skills that must read the current conversation: no fork.
- A personal variant of a team skill: give it its own name.

### Common mistakes

- Expecting `allowed-tools` to block other tools.
- Forking a skill whose job is to summarize the conversation it can no longer see.
- Shadowing a team skill with a same-named personal one.

## Path-specific rules
<!-- concepts: path-specific-rules, conditional-loading, rule-frontmatter -->

### Core concepts

- A rule in `.claude/rules/` with `paths` frontmatter loads only when Claude works with files matching its globs.
- `paths` is the only frontmatter field rules read. It accepts a YAML list or a comma-separated string.
- If the frontmatter doesn't parse, Claude Code ignores it and loads the rule **unscoped**. An unquoted `*` starts a YAML alias, so quote glob patterns: `paths: ["**/*.tf"]`. `claude --debug` shows the parse error.

### Decision rules

- Conventions for a file type spread across many directories (Terraform, tests, migrations): a path-scoped rule with a glob, not a `CLAUDE.md` in every directory.
- A rule that should apply even when no matching file is open: remove `paths`.

### Common mistakes

- Unquoted globs that silently turn a scoped rule into an always-on rule.
- Expecting a path-scoped rule to shape answers to general questions that touch no matching file.

## Plan mode and direct execution
<!-- concepts: plan-vs-direct, direct-execution, plan-mode, large-scale-changes, explore-subagent, review-before-edit -->

### Core concepts

- In plan mode, Claude reads files and proposes a plan but makes no edits until you approve. Enter it with `Shift+Tab` or `claude --permission-mode plan`.
- Plan mode suits changes with several valid approaches, architectural impact, or many files. Direct execution suits small, well-understood changes.
- Subagents, such as the built-in Explore agent, do discovery in their own context and return a summary, keeping the main conversation lean.

### Decision rules

- Clear, local fix (a stack trace pointing at one function): go direct.
- Migration across many files with an unknown mix of approaches: plan, then execute the approved plan.
- Must review before anything changes: plan mode, not a "don't edit" instruction.
- Heavy discovery before implementation: delegate it to a subagent.

### Common mistakes

- Planning trivial edits, or skipping planning for cross-cutting ones.
- Using file count as the only test.
- Using `/clear` to drop discovery noise, which also loses the findings.

## Iterative refinement
<!-- concepts: iterative-refinement, input-output-examples, test-driven-iteration, interview-pattern, interacting-issues -->

### Core concepts

- When prose is interpreted inconsistently, two or three concrete input and expected-output examples remove the ambiguity.
- Test-driven iteration: write tests for behavior, edge cases, and performance first, then share failures back to Claude.
- The interview pattern: in an unfamiliar domain, have Claude ask questions before implementing, to surface considerations you didn't know to mention.
- Problems that interact belong in one detailed message. Independent problems can be fixed one at a time.

### Common mistakes

- Answering inconsistency with more prose.
- Letting Claude write code and tests together, then trusting that they agree.
- Feeding interacting bugs one at a time, so each fix disturbs the other.

## Claude Code in CI/CD
<!-- concepts: ci-structured-output, json-schema-output, ci-review-iteration, duplicate-findings, independent-review, session-isolation, ci-context, bare-mode, ci-permissions, allowed-tools-flag, ci-test-generation -->

### Core concepts

- `claude -p` runs non-interactively and exits with a status code, so scripts can branch on success or failure.
- `--output-format json` returns the result with metadata. Adding `--json-schema` puts schema-conforming data in `structured_output`. Check that the field exists, because a run that ends without valid output leaves it out.
- In a `-p` run, calls that need approval are denied unless something approves them. `--allowedTools` pre-approves exactly what the job needs, for example `"Bash(npm test *)"`.
- `--bare` (recommended for CI, and planned as the future default for `-p`) skips auto-discovery of hooks, skills, MCP servers, auto memory, and `CLAUDE.md`. Pass context explicitly, for example with `--append-system-prompt-file`. Without `--bare`, `-p` loads `CLAUDE.md` as usual.
- A session that wrote code is a weak reviewer of that code. An independent instance reviews it as written.

### Decision rules

- Machine-readable findings: `--output-format json` plus `--json-schema`, not "respond in JSON".
- Re-running reviews after new commits: pass the earlier findings and ask only for new or still-open issues.
- Test generation: give Claude the existing tests and document fixtures and standards.
- Permissions: list the commands the job needs, not `bypassPermissions`.

### Common mistakes

- Parsing prose for JSON.
- Assuming `CLAUDE.md` reaches a `--bare` run.
- Having the generating session review its own changes.

## Checklist: what to do without notes

- [ ] Place an instruction in managed, user, project, or local `CLAUDE.md`, and say who receives it.
- [ ] Explain how two conflicting `CLAUDE.md` files behave, and how to resolve the conflict.
- [ ] Write an `@import` with a path relative to the importing file.
- [ ] Choose between `CLAUDE.md`, a rule, and a skill for a piece of guidance.
- [ ] Set skill frontmatter for manual-only invocation, forked execution, and an argument hint, and say what `allowed-tools` does and doesn't do.
- [ ] Write a path-scoped rule with correctly quoted globs.
- [ ] Decide between plan mode and direct execution for a described change.
- [ ] Pick examples, tests first, or the interview pattern for a refinement problem.
- [ ] Write a CI command with `-p`, structured output, scoped `--allowedTools`, and explicit context under `--bare`.
